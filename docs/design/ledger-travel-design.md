# 记账 + 旅行 数据项目设计方案

> 状态:草案 v2(已按评审意见修订)
> 日期:2026-08-23
> 范围:在 `DATA_ROOT` 下新增两个数据子项目(`ledger` 记账、`travel` 旅行),并在各自 `AGENTS.md` 中定义路由与数据约定。不修改框架源码(微信渠道的入站图片支持已内置,见 §5.3)。

## 1. 背景与目标

- **记账**:最常见的个人需求,支持多维度统计分析(按月/分类/标签/账户/收支趋势)。
- **旅行**:记录旅行中各类事件(文字 + 图片),后期产出可视化时间线,以及一张"我去过哪些地方"的中国地图;旅行中产生的消费也要能统计。

### 核心边界

1. **钱只进 `ledger`** —— 记账项目是金额的单一事实来源,总额永远完整。
2. **`travel` 只记事件** —— 旅行项目不存钱,只记事件/见闻/行程/图片。
3. **旅行花费 = 在 `ledger` 里打标签统计** —— 记账记录用 `tags` 约定 `旅行:<行程名>`(如 `旅行:2026北京`),"这次旅行花了多少"就是对标签的一次筛选。
4. **一条消息路由一个项目** —— 消费类消息 → `ledger`,事件类消息 → `travel`;不做跨项目双写。
5. **混合消息仲裁** —— 只要句子里带金额或真正的消费动词(花了/买了/付了/订了/花了多少钱…),一律路由到 `ledger`;这类句中的体验描述("太壮观了")不进时间线,这个代价接受(理想情况是分两条发)。反向:纯体验句(无金额)进 `travel`。名词(如"门票")单独出现无金额时不判为消费。

## 2. 调研:GitHub 现成记账数据结构参考

| 方案 | 数据模型 | 结论 |
|---|---|---|
| **beancount / ledger-cli**(纯文本复式记账) | 账户树(Assets/Liabilities/Expenses…)、`open`/`close`、交易 = ≥2 条 posting、payee + narration、commodity/prices、balance assertion | 审计性最强,但复式记账心智负担重,对"随手记一笔"的个人场景过重;不做主模型 |
| **九快记账 moneynote**(开源,500+ star) | 多账本、收支记录(收入/支出/转账)、**分类树(父子层级)**、**标签**、资产账户、多币种、账单附件、报表统计 | 功能最全的个人记账参考,字段设计值得借鉴 |
| **钱迹 moneytracker**(开源 Web 记账) | 简洁的"分类 + 金额 + 日期 + 备注"单式流水 | 印证单式流水足够用 |

**共识模型(本方案采用)**:`单式流水记录` + `分类树` + `标签` + `资产账户`。金额用**整数分**存储避免浮点误差。M1 不做转账(见 §4.1 与 §8)。

```

│   ├── AGENTS.md               # 路由提示(首段) + 记账约定
│   ├── data/
│   │   ├── ledger.json         # 流水记录(唯一金额来源)
│   │   └── meta.json           # 分类树 / 账户 / 行程标签登记表
│   ├── scripts/build.py        # 校验 + 生成统计报告(ledger.html)
│   └── web/                    # 生成物:统计仪表盘(静态、自包含,入库)
└── travel/                     # 独立 git 仓库(框架自动提交)
    ├── AGENTS.md               # 路由提示(首段) + 旅行事件约定
    ├── data/
    │   ├── events.json         # 时间线事件(文字 + 图片引用 + 地点)
    │   └── cities.json         # 城市→省份→坐标表(vendored,供 build.py 使用)
    ├── photos/                 # 事件配图:微信入站图片由框架自动落盘;其他渠道手动放入
    ├── scripts/build.py        # 校验 + 生成 timeline.html / map.html
    └── web/                    # 生成物:时间线 + 中国地图(入库)
```

### AGENTS.md 编写纪律(路由读取规则,必须遵守)

框架路由只读"**去掉首个 `#` 标题后的前 300 字符**"(`system-prompt.ts` `projectSummary`, `SUMMARY_CHARS = 300`),并用正则提取 `路由提示(?:（botler-agent）)?[:：]…「…」` 的关键词列表。

因此:

1. **路由提示块必须紧跟 H1,放在正文第一段** —— 放在文档后半段路由阶段根本看不到,消息会路由失败。
2. **格式严格**:`路由提示（botler-agent）：涉及「关键词 / 关键词」…`,括号**必须用全角 `（botler-agent）`**(半角 `(botler-agent)` 无法被正则匹配),冒号全角半角均可,关键词列表用「」包裹并放在该行的第一个「」位置。
3. 关键词列表尽量精简,确保落在 300 字符截断内。

## 4. 记账项目设计(`ledger`)

### 4.1 数据文件结构

**`data/ledger.json`** —— 唯一的金额流水:

```json
{
  "version": 1,
  "currency": "CNY",
  "records": [
    {
      "id": "L20260823-001",
      "date": "2026-08-23",
      "type": "expense",
      "amount_cents": 20000,
      "account": "微信",
      "category": ["餐饮", "午餐"],
      "tags": ["旅行:2026北京"],
      "payee": "全聚德",
      "note": "北京旅行午餐",
      "created_at": "2026-08-23T12:30:00+08:00"
    }
  ]
}
```

**金额换算规则(写死)**:元 → 分 = ×100,存整数分。**Worked example**:25.90 元 → `amount_cents: 2590`;200 元 → `20000`。禁止存小数、禁止用字符串金额。

字段说明:

| 字段 | 说明 |
|---|---|
| `id` | 唯一 ID,`L<YYYYMMDD>-<seq>`;`seq` 由 agent 扫描当日已有记录的最大序号 +1,唯一性由 `build.py` 兜底校验 |
| `date` | 记账日期(实际交易日) |
| `type` | `expense` / `income`(**M1 无 `transfer`**,见 §8) |
| `amount_cents` | 金额,**正整数分**,见上方换算规则 |
| `account` | 资产账户,取自 `meta.json`;用户未指定时默认「微信」 |
| `category` | 分类路径数组,**父级在前**(如 `["餐饮","午餐"]`),聚合时按数组逐级向上 roll up |
| `tags` | 多维度标签;**旅行消费统一用 `旅行:<行程名>`**。`meta.json.tags` 是"行程登记表":新行程首次记账前,agent 先 append `旅行:<名>` 进登记表再写记录(见 §4.2 校验的容错) |
| `payee` | 交易对象/商户,可空 |
| `note` | 备注,可空 |

**`data/meta.json`** —— 分类树、账户与行程标签登记表(agent 写入前分类/账户必须从这里取值):

```json
{
  "categories": [
    { "name": "餐饮", "children": ["早餐", "午餐", "晚餐", "饮料", "零食"] },
    { "name": "交通", "children": ["公交地铁", "打车", "加油", "停车", "机票", "高铁"] },
    { "name": "住宿", "children": ["酒店"] },
    { "name": "旅行", "children": ["门票", "纪念品"] },
    { "name": "购物", "children": [] },
    { "name": "居住", "children": ["房租", "水电煤"] },
    { "name": "医疗", "children": [] },
    { "name": "娱乐", "children": [] },
    { "name": "人情", "children": [] },
    { "name": "其他", "children": [] }
  ],
  "accounts": ["现金", "支付宝", "微信", "银行卡", "信用卡"],
  "tags": ["旅行:2026北京"]
}
```

> **category 与 tag 正交(重要,避免把行程消费全塞进「旅行」分类)**:`category` 回答"这笔钱花在**哪类东西**上"(餐饮/交通/住宿/旅行门票…),按消费性质选,**不因为正在旅行就把消费挂到「旅行」分类**;`tag 旅行:<行程名>` 回答"这笔钱属于**哪趟行程**",用于把跨分类的消费聚合成一趟。一趟行程:午饭走 `["餐饮","午餐"]`、机票走 `["交通","机票"]`、只有门票才走 `["旅行","门票"]`——靠同一个 tag 聚合出该行程的分类明细。否则全塞进「旅行」分类,§4.2 的"标签维度→行程分类明细"就退化成单一分类、没有明细可看。

### 4.2 统计分析 + build.py 校验

**统计能力**(`scripts/build.py` 产出 `web/ledger.html`,单文件静态仪表盘,Python 标准库):

1. **时间维度**:月度收入/支出/结余趋势、同比/环比;
2. **分类维度**:分类树逐级聚合、占比(饼图/柱状图);
3. **标签维度**:按标签聚合,例如 `旅行:2026北京` → 该行程总花费、日均、分类明细;
4. **账户维度**:各支付方式支出占比;
5. **交易对象**:`payee` Top-N;
6. **收支结构**:收入 vs 支出、储蓄率。

**build.py 校验规则(`--dry-run`,框架的"JSON 合法"兜底之外)**:

- `amount_cents` 为**正整数**(元→分换算错误的高频场景);
- `id` **全局唯一**(防 seq 撞号);
- `category` 路径存在于 `meta.json`(严格);
- `account` 存在于 `meta.json`(严格);
- `tags` 只做 `旅行:` 前缀格式校验,**不强制在字典内**——容忍首笔漏登记(容错);规范做法是先登记再写;
- 单笔 > ¥10000 给出**告警**(防多写一个零),不报错阻断。

### 4.3 AGENTS.md 路由提示与约定(草稿,路由提示必须放首段)

```markdown
# AGENTS.md

路由提示（botler-agent）：涉及「记账 / 账 / 消费 / 花了 / 支出 / 收入 / 工资 / 报销 / 账单 / 开销 / 花了多少钱 / 结余」的记录或查询消息都属于本项目。任何涉及金额的消息一律路由到本项目,即使发生在旅行中(旅行消费在记账里打 旅行:<行程名> 标签)。

## 混合消息仲裁

句子里只要带金额或真正的消费动词(花了 / 买了 / 付了 / 订了 / 花了多少钱…),一律按记账处理;其中的体验描述不记录。「门票」等名词单独出现且无金额(如"故宫门票拍得真好看")不判为消费。

## 写入后必须刷新

任何写入 data/ledger.json 后执行 `python3 scripts/build.py`(可先用 `--dry-run` 校验),否则仪表盘不刷新。
```

## 5. 旅行项目设计(`travel`)

### 5.1 数据文件结构

**`data/events.json`** —— 时间线事件:

```json
{
  "version": 1,
  "events": [
    {
      "id": "E20260823-001",
      "at": "2026-08-23T14:30:00+08:00",
      "place": "故宫博物院",
      "city": "北京",
      "trip": "2026北京",
      "text": "现在进入故宫了,感觉很棒很庄严",
      "images": ["photos/2026-08-23-8f3a9c.jpg"]
    }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `id` | 唯一 ID,`E<YYYYMMDD>-<seq>`,规则同 ledger,`build.py` 校验唯一 |
| `at` | 事件时间(ISO 8601,含时区) |
| `place` | 具体地点(景点/场馆名) |
| `city` | 城市,用于地图聚合;名字与 `data/cities.json` 做后缀归一化匹配 |
| `trip` | 行程名(可空,用于按行程分组);**命名须与 ledger 标签一致**:travel 用 `trip: "2026北京"` ↔ ledger 用 tag `旅行:2026北京` |
| `text` | 事件描述 |
| `images` | 图片路径数组,**相对 travel 项目根目录**;微信入站图片由框架落在 `photos/`,agent 引用 `photos/<文件名>` |

**`data/cities.json`** —— 城市表(约 300 个主要城市,**vendored 成数据文件,不硬编码在 build.py**):

```json
{
  "cities": [
    { "city": "北京", "province": "北京市", "lat": 39.9042, "lng": 116.4074 }
  ]
}
```

- `build.py` 读取时做**后缀归一化**(去掉 省/市/自治区/特别行政区)后再匹配;
- 匹配不上 → **告警并跳过**,不阻断构建(生僻地名不影响出图)。

### 5.2 可视化

**时间线 `web/timeline.html`**:反向时间轴,按天/行程分组,每条事件展示文字 + 图片(如有)。纯静态 HTML/CSS/JS,数据由 `build.py` 内嵌为 JSON,单文件自包含、离线可用。

**旅行消费与时间线的弱关联(重要,接受)**:时间线想把"14:30 故宫门票 ¥80"穿插进去,只能靠 ledger 的 `旅行:<行程名>` 标签 + 日期时间与 travel 事件做 join,**无法精确对应"这条事件就是这笔钱"**。

- 命名统一:travel `trip` ↔ ledger `旅行:` 标签,`build.py` 对标签做 `旅行:` 前缀剥离后匹配行程名;
- 同一天多笔、时区、时间粒度不一致都会导致无法一一对应——**接受它**:时间线只按"当天/当行程"汇总金额,不尝试逐事件配对。

**中国地图 `web/map.html`**:两张图——省级高亮(去过哪些省)+ 城市点标记(在哪些城市停留过)。两种可选方案(都需要**一次性**下载并 commit 中国地图数据资产):

| 方案 | 交互 | 依赖 | 与 cook 自包含风格 |
|---|---|---|---|
| **A. 静态 SVG 高亮**(推荐) | 基础 hover | 内嵌一份中国省级 SVG(几百 KB) | 完全自包含,Python 生成即可 |
| B. echarts 方案 | 缩放/提示框 | vendored `echarts.min.js` + 省级 GeoJSON | 需引入 JS 库 |

### 5.3 图片记录方案(微信渠道已内置支持)

框架已内置微信入站图片管线(`channels/wechat/download.ts` + `runner.ts`),一条"照片 + 说明"的消息完整走通:

1. 微信 IMAGE 消息 → CDN 下载 + AES-128-ECB 解密 → 解码出原始字节;
2. 字节**内联给模型**做视觉识别(模型需声明 `vision: true`,providers.json 默认开启);
3. 路由确定项目后,框架把原图落盘到 `DATA_ROOT/<project>/photos/<日期>-<随机>.<ext>`;
4. agent 收到的执行文本会附加提示:`[图片已保存到] travel/photos/<…>(可在记录中引用这些相对路径)`;
5. 照片与紧跟的说明文字默认**合并为一条任务**(`WECHAT_IMAGE_BATCH_SECONDS`,默认 60s,`0` 关闭);
6. 图片落盘即视为数据变更,随该子项目自动 git 提交;未路由成功的消息不会落盘。

**旅行项目用法**(零框架改动):

- 微信发「现在进入故宫了,感觉很棒很庄严」+ 照片 → 路由到 `travel` → 照片落在 `travel/photos/2026-08-23-xxxx.jpg` → agent 把项目内相对路径 `photos/2026-08-23-xxxx.jpg` 写进 `events.json` 的 `images` 字段。
- agent 要把框架提示的 `travel/photos/…` 去掉 `travel/` 前缀,以项目根为基准引用(写进 travel 的 AGENTS.md)。

**注意与限制**:

- 收图管线目前**只覆盖微信渠道**;Telegram / Feishu / CLI 仍只传文字,这几个渠道的图片需手动放入 `travel/photos/` 后引用文件名(备用方案)。
- `photos/` 是框架约定的固定目录,travel 项目统一用它存放入站图片,不要另建 `images/`。
- **孤儿图片**:微信图先落盘、agent 后决定是否引用;写记录失败或未引用会在 `photos/` 积攒未引用文件,且都会进 git。缓解:`build.py` 输出"photos/ 中未被 events.json 引用的文件"清单,供定期人工清理。
- **git 膨胀**:框架对子项目执行 `git add -A`(`git.ts:28`),照片二进制随每次提交永久进历史,多年旅行后仓库会变大。选项:git-lfs / 单独备份 / 接受增长。**M1 接受增长**,后期再决定。

### 5.4 AGENTS.md 路由提示与约定(草稿,路由提示必须放首段)

```markdown
# AGENTS.md

路由提示（botler-agent）：涉及「旅行 / 旅游 / 在…(地点) / 去了 / 逛了 / 景点 / 行程 / 游记 / 打卡 / 配图 / 照片 / 图片 / 时间线」的事件记录或查询消息都属于本项目。凡涉及金额/消费的消息一律归记账项目,本项目不记录任何金额。

任何写入 data/events.json 后执行 `python3 scripts/build.py`,否则时间线/地图不刷新。
```

## 6. 框架能力核对

| 能力 | 状态 | 说明 |
|---|---|---|
| 一个消息一个项目(路由) | ✅ 支持 | 路由提示必须放 AGENTS.md 首段 300 字符内,格式见 §3 |
| 金额只存一处,旅行花费用标签筛 | ✅ 支持 | 纯数据约定 |
| JSON 合法性兜底 + 自动 git 提交 | ✅ 支持 | 框架内置;提交范围是**整个子项目**(`git add -A`) |
| 生成静态可视化(`run` 执行项目内脚本) | ✅ 支持 | 沿用 cook `build.py` 模式;AGENTS.md 须显式要求写入后运行 |
| 聊天图片进入 agent(微信渠道) | ✅ 支持 | 入站图片解码后内联给模型做视觉识别,并落盘到 `<项目>/photos/`,agent 拿到相对路径引用;Telegram / Feishu / CLI 暂不支持 |
| 跨项目双写(一条消息写两个项目) | ⚠️ 可行但不用 | 白名单允许,但为数据一致性与路由清晰,刻意不用 |

## 7. 落地步骤
